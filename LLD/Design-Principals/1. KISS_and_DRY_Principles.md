# KISS & DRY Principles — Simplified Guide (with PHP Examples)

> A practical companion to the AlgoMaster LLD lessons on KISS and DRY, rewritten simply with PHP code so you can *see* the difference, not just read about it.

---

## 1. KISS — Keep It Simple, Stupid

### The idea in one line
> Solve today's problem in the simplest way that works. Don't build machinery for problems you don't have yet.

### Why engineers violate it
When we learn design patterns, interfaces, and abstractions, there's a natural urge to use them *everywhere* — even for a simple task — because it "feels" more professional. This is called **over-engineering**, and KISS is the principle that guards against it.

---

### ❌ Example: A calculator that violates KISS

Imagine you just need to add two numbers. An over-engineered PHP version might look like this:

```php
interface Operation {
    public function execute(float $a, float $b): float;
}

class AddOperation implements Operation {
    public function execute(float $a, float $b): float {
        return $a + $b;
    }
}

class OperationFactory {
    public static function create(string $type): Operation {
        return match ($type) {
            'add' => new AddOperation(),
            default => throw new InvalidArgumentException("Unsupported operation"),
        };
    }
}

class Calculator {
    public function calculate(string $type, float $a, float $b): float {
        $operation = OperationFactory::create($type);
        return $operation->execute($a, $b);
    }
}

// Usage
$calc = new Calculator();
echo $calc->calculate('add', 2, 3); // 5
```

For a requirement that is *only* "add two numbers," this is a lot of ceremony: an interface, a class per operation, and a factory — three files/classes to do what one line can do.

### ✅ The simple, KISS-compliant version

```php
class Calculator {
    public function add(float $a, float $b): float {
        return $a + $b;
    }
}

$calc = new Calculator();
echo $calc->add(2, 3); // 5
```

**One class, one method. Done.** If tomorrow you actually need subtract, multiply, divide, and pluggable operations — *that's* when the factory + interface design earns its complexity. Not before.

---

### The Complexity Cycle
This is the trap KISS protects you from:

1. You anticipate future requirements ("what if we need 10 operations later?")
2. You add abstraction layers to "future-proof" the code
3. The code becomes harder to read, test, and onboard new developers into
4. The future requirement either never comes, or comes in a different shape than you guessed — so the abstraction was wasted (or wrong) anyway

### Why complexity is dangerous
- **Harder to read** — new developers (or you, in 6 months) take longer to understand what's happening
- **Harder to debug** — more layers means more places a bug can hide
- **Harder to change** — ironically, code built to be "flexible for the future" often makes the *actual* future change harder, because you have to work around the wrong abstraction
- **More bugs** — every extra class/branch is more surface area for mistakes

### Signs you're violating KISS
- You created an interface with only **one** implementation
- You added a design pattern "because it's a best practice," not because you have the problem it solves
- You're passing configuration/flags to handle cases that don't exist yet
- Your class or function needs a paragraph to explain what it does
- You're solving a problem you *imagine* the business might have, not one it *has*

### How to apply KISS
1. **Write the dumbest solution that works first.** Optimize/abstract only when you feel real pain (duplicated code, changing requirements).
2. **Prefer functions and simple classes over patterns**, until you have a second or third variation that proves you need the pattern.
3. **Ask: "What is the actual current requirement?"** — not the requirement you're guessing about.
4. **Delete before you add.** If you can remove a class/layer and the code still reads clearly, remove it.

### When NOT to simplify
KISS doesn't mean "avoid all structure" or "never use design patterns." It means don't add structure *before it's needed*. Some cases where more structure is justified from day one:
- You **already know** (not guess) that multiple operation types are coming — e.g., a payment system that must support Stripe, PayPal, and Razorpay from launch
- You're building a **library/framework** that other teams will extend
- Regulatory/business rules that are genuinely complex (simplifying would produce *wrong* behavior, not just ugly code)

> KISS is about **avoiding unnecessary complexity** — not avoiding all complexity. Some problems are genuinely complex; simplify them as much as possible, not one bit more.

## 2. DRY — Don't Repeat Yourself

### The idea in one line
> Every piece of knowledge (a business rule, a calculation, a piece of logic) should exist in **exactly one place** in your codebase.

Note: DRY is about **duplicated knowledge/logic**, not duplicated-looking text. Two pieces of code that *look* similar but represent different business rules are **not** a DRY violation (more on this below).

---

### ❌ Example: Repeated logic

```php
class OrderService {
    public function calculateOnlineOrderTotal(float $price, int $qty): float {
        $subtotal = $price * $qty;
        $tax = $subtotal * 0.18;       // 18% GST
        $discount = $subtotal > 1000 ? $subtotal * 0.1 : 0;
        return $subtotal + $tax - $discount;
    }

    public function calculateStoreOrderTotal(float $price, int $qty): float {
        $subtotal = $price * $qty;
        $tax = $subtotal * 0.18;       // same 18% GST, copy-pasted
        $discount = $subtotal > 1000 ? $subtotal * 0.1 : 0; // same discount rule, copy-pasted
        return $subtotal + $tax - $discount;
    }
}
```

The **tax rule** and **discount rule** are business knowledge. Right now they're written twice. The problem: if the GST rate changes from 18% to 20%, you must remember to update it in **every** place it was copy-pasted. Miss one, and you have a silent bug (and possibly a compliance issue).

### The Rule of Three
A practical guideline for *when* to remove duplication:
- **1st time** you write some logic → just write it.
- **2nd time** you need the same logic → note it, but copy-paste is still often fine (don't guess at the shared abstraction yet).
- **3rd time** the same logic shows up → now extract it into a shared method/class. By the third occurrence, you have enough real examples to know what the *correct* shared abstraction actually looks like.

This protects you from the opposite mistake — abstracting after seeing only one or two cases and getting the abstraction wrong (which is itself a KISS violation!).

### ✅ Applying DRY

```php
class OrderPricingCalculator {
    private const TAX_RATE = 0.18;
    private const DISCOUNT_THRESHOLD = 1000;
    private const DISCOUNT_RATE = 0.10;

    public function calculateTotal(float $price, int $qty): float {
        $subtotal = $price * $qty;
        $tax = $subtotal * self::TAX_RATE;
        $discount = $subtotal > self::DISCOUNT_THRESHOLD
            ? $subtotal * self::DISCOUNT_RATE
            : 0;

        return $subtotal + $tax - $discount;
    }
}

class OrderService {
    public function __construct(private OrderPricingCalculator $calculator) {}

    public function calculateOnlineOrderTotal(float $price, int $qty): float {
        return $this->calculator->calculateTotal($price, $qty);
    }

    public function calculateStoreOrderTotal(float $price, int $qty): float {
        return $this->calculator->calculateTotal($price, $qty);
    }
}
```

Now the tax rate and discount rule live in **exactly one place** (`OrderPricingCalculator`). Change the GST rate once, and every caller is correct automatically.

### Why repetition is a problem
- **Bugs from partial updates** — you fix a rule in one place and forget the copy elsewhere
- **Inconsistent behavior** — two "copies" of logic quietly drift apart over time as different developers touch them
- **More code to test and maintain** — the same test scenario has to be written and re-verified in multiple places

### Practical example: Notification system

```php
// ❌ Violates DRY — email formatting/sending logic repeated per notification type
class OrderNotifier {
    public function sendOrderConfirmation(string $email, string $orderId): void {
        $subject = "Order Confirmed";
        $body = "Your order #$orderId has been confirmed.";
        mail($email, $subject, $body); // pretend mail sending logic
    }

    public function sendShippingUpdate(string $email, string $orderId): void {
        $subject = "Order Shipped";
        $body = "Your order #$orderId has shipped.";
        mail($email, $subject, $body); // duplicated sending logic
    }
}
```

```php
// ✅ DRY — shared sending logic, only the content changes
class EmailSender {
    public function send(string $email, string $subject, string $body): void {
        mail($email, $subject, $body);
        // logging, retries, etc. live here — in ONE place
    }
}

class OrderNotifier {
    public function __construct(private EmailSender $emailSender) {}

    public function sendOrderConfirmation(string $email, string $orderId): void {
        $this->emailSender->send(
            $email,
            "Order Confirmed",
            "Your order #$orderId has been confirmed."
        );
    }

    public function sendShippingUpdate(string $email, string $orderId): void {
        $this->emailSender->send(
            $email,
            "Order Shipped",
            "Your order #$orderId has shipped."
        );
    }
}
```

If tomorrow you need to add retry logic, logging, or switch from `mail()` to an API-based provider (SendGrid, SES), you change it **once** inside `EmailSender`.

### When it's OKAY to repeat (important!)
This is the part people most often get wrong. **Not all similar-looking code is a DRY violation.**

```php
// These LOOK similar but represent DIFFERENT business rules —
// merging them would be a mistake, not a DRY win.

class DiscountPolicy {
    public function calculateStudentDiscount(float $amount): float {
        return $amount * 0.15; // 15% — set by marketing team, changes independently
    }

    public function calculateSeniorCitizenDiscount(float $amount): float {
        return $amount * 0.15; // happens to also be 15% today — set by a DIFFERENT policy
    }
}
```

Even though both currently return `amount * 0.15`, they represent **two separate business decisions** made by different stakeholders that just happen to have the same value *today*. If you merge them into one shared method and the "student discount" changes to 20% next quarter, you'd accidentally change the senior citizen discount too.

**Rule of thumb:** Ask *"Is this duplication because it's the same rule, or because two different rules coincidentally look the same right now?"*
- Same rule, same reason → extract it (DRY).
- Different rule, same value by coincidence → keep them separate.

## 3. How KISS and DRY Work Together

These two principles can *pull in opposite directions* if you're not careful:

| | KISS pushes you to... | DRY pushes you to... |
|---|---|---|
| Behavior | Keep code simple, even if it means some duplication | Remove duplication, even if it adds a layer of abstraction |
| Risk if overdone | Copy-pasted logic that drifts out of sync | Over-abstracted code that's hard to follow (violates KISS!) |

**The balance:** Use DRY once you have **proven, repeated** duplication of the *same* knowledge (Rule of Three). Use KISS to make sure the abstraction you build to remove that duplication is the **simplest one that solves it** — not a generic, speculative framework.

A good mental checklist before extracting shared code:
1. Is this the *same* business rule, not a coincidence? (DRY check)
2. Have I seen this pattern at least 2–3 times for real? (Rule of Three)
3. Is my new shared class/method still simple to read in isolation? (KISS check)

If all three are "yes" — extract it. Otherwise, leave the code as-is for now.

---

## 4. Quick Reference

**KISS**
- Solve the problem you have, not the one you imagine
- Prefer plain functions/classes over patterns until proven necessary
- Red flag: interface with one implementation, "just in case" flexibility

**DRY**
- One piece of business knowledge = one place in code
- Use the Rule of Three before abstracting
- Red flag: same *rule* copy-pasted in 3+ places
- Not a violation: similar-looking code that represents genuinely different rules

**Together:** Simplify first. Deduplicate when duplication is proven and real. Keep whatever you extract simple too.
