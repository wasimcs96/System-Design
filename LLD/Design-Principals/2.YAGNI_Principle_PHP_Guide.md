# YAGNI Principle — Simplified Guide (with PHP Examples)

> "You Aren't Gonna Need It" — a companion to the KISS & DRY guide, same style: simple explanation, PHP before/after code, and when to actually break the rule.

---

## 1. The idea in one line
> Don't build a feature, abstraction, or flexibility until you actually need it — not when you *think* you might need it someday.

YAGNI is closely related to KISS, but it's more specific: KISS is about keeping the code you write *simple*. YAGNI is about **not writing code at all** until there's a real, current requirement for it.

---

## 2. Why engineers violate it

The usual reasoning sounds responsible:
- "Let's add a `type` field now, we might support multiple payment methods later."
- "Let's make this configurable, in case requirements change."
- "Let's build a plugin system, so we can add features without touching core code."

All of these *feel* like good engineering. The problem: you're guessing about the future, and you're paying the cost of that guess **today**, in code that has to be written, tested, documented, and maintained — for a requirement that may never arrive, or may arrive in a completely different shape than you guessed.

---

## 3. ❌ Example: A notification system built for imagined flexibility

```php
interface NotificationChannel {
    public function send(string $to, string $message): void;
}

class EmailChannel implements NotificationChannel {
    public function send(string $to, string $message): void {
        mail($to, "Notification", $message);
    }
}

interface NotificationStrategy {
    public function decideChannel(array $userPrefs): NotificationChannel;
}

class DefaultNotificationStrategy implements NotificationStrategy {
    public function decideChannel(array $userPrefs): NotificationChannel {
        // Only ever returns EmailChannel — SMS/Push channels don't exist yet
        return new EmailChannel();
    }
}

class NotificationConfig {
    public bool $allowRetry = false;
    public int $maxRetries = 0;
    public bool $allowScheduling = false; // feature doesn't exist anywhere
    public ?string $priorityQueue = null; // no priority queue system exists
}

class NotificationService {
    public function __construct(
        private NotificationStrategy $strategy,
        private NotificationConfig $config
    ) {}

    public function notify(string $to, string $message, array $userPrefs): void {
        $channel = $this->strategy->decideChannel($userPrefs);
        $channel->send($to, $message);
        // $this->config->allowRetry, allowScheduling, priorityQueue are never used
    }
}
```

The actual requirement was: **"send an email when an order is placed."** But this code has a strategy pattern, a config object with unused flags, and an interface for channels that don't exist yet. Every one of those things has to be understood by the next developer, even though none of it does anything real today.

---

## 4. ✅ The YAGNI-compliant version

```php
class NotificationService {
    public function notify(string $to, string $message): void {
        mail($to, "Notification", $message);
    }
}

// Usage
$service = new NotificationService();
$service->notify('user@example.com', 'Your order has been placed.');
```

**One method, does exactly what's needed.** When SMS notifications become a *real* requirement (not a guess), that's when you introduce a `NotificationChannel` interface — and by then, you'll know exactly what the interface needs to look like, because you'll have two real implementations (email + SMS) to design it from.

## 5. A more realistic case: "configurable" that never gets configured

```php
// ❌ Built "just in case" the business wants different tax rates per country someday
class InvoiceCalculator {
    public function __construct(
        private float $taxRate = 0.18,
        private bool $enableMultiCurrency = false,
        private ?string $currencyConverterApiKey = null,
        private array $countryTaxOverrides = []
    ) {}

    public function calculate(float $amount, ?string $countryCode = null): float {
        $rate = $this->countryTaxOverrides[$countryCode] ?? $this->taxRate;
        // $enableMultiCurrency and $currencyConverterApiKey are never actually used
        return $amount + ($amount * $rate);
    }
}
```

```php
// ✅ YAGNI — the business currently only sells in India at 18% GST
class InvoiceCalculator {
    private const TAX_RATE = 0.18;

    public function calculate(float $amount): float {
        return $amount + ($amount * self::TAX_RATE);
    }
}
```

If multi-country tax support becomes a real requirement, you add it then — with full knowledge of what "country tax override" actually needs to mean (flat rate? tiered? VAT-exempt categories?). Guessing now just means you'll likely have to redo it anyway.

## 6. Signs you're violating YAGNI

- You're adding a parameter, config flag, or field that nothing in the codebase currently reads
- You're building an abstraction (interface, factory, strategy) for a **second case that doesn't exist yet**
- You justify code with "we might need this later" rather than pointing to an actual ticket/requirement
- You're building a generic/plugin-style system before you have even two concrete plugins to base it on
- Code review comments include "why does this exist?" and the answer is "future-proofing"

---

## 7. How to apply YAGNI

1. **Build for the requirement in front of you.** Not the roadmap, not the "what if."
2. **Let real repetition/need drive abstraction**, not speculation (this is where YAGNI and DRY's "Rule of Three" reinforce each other).
3. **When a stakeholder says "we might need X later,"** ask if it's a committed near-term requirement or a guess. If it's a guess, don't build it — note it for later instead.
4. **Delete unused flexibility** you find in the codebase (unused config options, interfaces with one implementation) when you touch that code.
5. **Trust that well-written simple code is easy to extend later.** YAGNI isn't an excuse for messy code — it's a promise that *if* you keep things simple and clean now, adding the real feature later will be easier than guessing wrong now.

---

## 8. When NOT to apply YAGNI

YAGNI doesn't mean "never think ahead" — it means don't **implement** for the future, don't necessarily ignore it in your design's shape. Some cases where a bit of forward design is reasonable:

- **Known, committed requirements** — if your team has an approved roadmap item for "SMS support in Q3," it's reasonable to at least name your class `EmailChannel` instead of `NotificationService`, so adding `SmsChannel` later is a smaller change. That's a naming/shape choice, not built-but-unused code.
- **Expensive-to-change decisions** — database schema, public API contracts, core domain model. Getting these "roughly right" early is cheaper than a full guess-free build, because changing them later is very costly. This is a judgment call, not a blank check to speculate freely.
- **Regulatory certainty** — e.g., you *know* a compliance requirement is coming next quarter because it's law, not a guess.

The distinction: **design decisions that cost little now and save a lot later are fine to consider. Actual code/features for use cases that don't exist yet are not.**

---

## 9. YAGNI vs KISS vs DRY — how they relate

| Principle | Question it asks | Failure mode if ignored |
|---|---|---|
| **YAGNI** | Do I need to build this *at all*, right now? | Unused code, speculative abstractions |
| **KISS** | Is this the simplest way to build what I *do* need? | Overcomplicated code for a real requirement |
| **DRY** | Am I repeating the *same* knowledge in multiple places? | Copy-pasted logic that drifts out of sync |

A simple way to sequence them while coding:
1. **YAGNI** — Do I actually need this right now? If no, stop.
2. **KISS** — Given that I do need it, what's the simplest implementation?
3. **DRY** — Once I see the same real logic 2–3 times, extract it — simply.

---

## 10. Quick Reference

**YAGNI**
- Build only what's needed for a real, current requirement
- "We might need it later" is not a reason to build it now
- Red flag: unused config flags, interfaces with a single implementation, plugin systems with one plugin
- OK to bend: cheap-to-decide-now / expensive-to-change-later decisions (schema, public APIs) for *known* (not guessed) future needs

**In one sentence:** Write the code the current requirement needs — nothing more — and trust that simple code is easy to extend when the real future requirement actually shows up.
