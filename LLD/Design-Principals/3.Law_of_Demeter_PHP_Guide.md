# Law of Demeter (LoD) — Simplified Guide (with PHP Examples)

> Also called the **"Principle of Least Knowledge"** — a companion to the KISS, DRY, and YAGNI guides, same style.

---

## 1. The idea in one line
> An object should only talk to its **immediate friends** — not to strangers reached through those friends.

In practice: **don't chain method/property access across multiple objects.** If you write code like `$a->getB()->getC()->getD()->doSomething()`, you've likely broken the Law of Demeter.

---

## 2. The Problem — a "train wreck" of chained calls

Imagine a ride-hailing app. You want to notify the driver's phone when a ride is assigned.

```php
class Phone {
    public function __construct(private string $number) {}
    public function getNumber(): string {
        return $this->number;
    }
}

class Driver {
    public function __construct(private Phone $phone) {}
    public function getPhone(): Phone {
        return $this->phone;
    }
}

class Vehicle {
    public function __construct(private Driver $driver) {}
    public function getDriver(): Driver {
        return $this->driver;
    }
}

class Ride {
    public function __construct(private Vehicle $vehicle) {}
    public function getVehicle(): Vehicle {
        return $this->vehicle;
    }
}

class RideNotifier {
    public function notifyDriver(Ride $ride, string $message): void {
        // ❌ reaching through Ride -> Vehicle -> Driver -> Phone
        $number = $ride->getVehicle()->getDriver()->getPhone()->getNumber();
        $this->sendSms($number, $message);
    }

    private function sendSms(string $number, string $message): void {
        echo "Sending SMS to $number: $message\n";
    }
}
```

This chain — `$ride->getVehicle()->getDriver()->getPhone()->getNumber()` — is the classic "train wreck." `RideNotifier` doesn't just know about `Ride`; it knows that a `Ride` has a `Vehicle`, that a `Vehicle` has a `Driver`, that a `Driver` has a `Phone`, and that a `Phone` has a `getNumber()` method. That's **four classes' worth of internal structure** leaking into one method that just wants to send a text.

---

## 3. What's wrong with this?

- **Tight coupling to internal structure.** `RideNotifier` is now coupled not just to `Ride`, but to `Ride`'s internals, and *their* internals, and so on. Change any link in that chain (say, `Driver` now has multiple phones) and this code breaks — even though `RideNotifier` has nothing conceptually to do with `Vehicle` or `Driver`.
- **Fragile to refactoring.** If tomorrow `Vehicle` no longer stores the `Driver` directly (say, drivers get reassigned dynamically and it's looked up elsewhere), every place with a chain like this breaks.
- **Leaks responsibility.** Deciding "how to get a driver's phone number" is arguably `Ride`'s job (or `Vehicle`'s), not `RideNotifier`'s. `RideNotifier` should just be able to ask, "hey Ride, give me the driver's phone number" without knowing *how* that's structured internally.
- **Hard to test.** To unit test `notifyDriver()`, you now need to construct a full `Ride` → `Vehicle` → `Driver` → `Phone` object graph, even though conceptually you just want to test "does it send the right SMS."

---

## 4. Enter: The Law of Demeter

Formally, a method `M` of an object `O` should only call methods on:
1. `O` itself
2. Objects passed as parameters to `M`
3. Objects `M` creates/instantiates itself
4. `O`'s own direct properties/fields

...but **not** on objects returned by calling methods on any of the above (that's the "talking to a stranger" — a friend-of-a-friend).

A common paraphrase: **"Only talk to your immediate friends. Don't talk to strangers."**

---

## 5. Refactoring with LoD in mind

The fix is to let each object provide the information its callers actually need, instead of exposing its internal structure. This is often called **"Tell, Don't Ask."**

```php
class Phone {
    public function __construct(private string $number) {}
    public function getNumber(): string {
        return $this->number;
    }
}

class Driver {
    public function __construct(private Phone $phone) {}

    // Driver exposes what callers need directly
    public function getPhoneNumber(): string {
        return $this->phone->getNumber();
    }
}

class Vehicle {
    public function __construct(private Driver $driver) {}

    public function getDriverPhoneNumber(): string {
        return $this->driver->getPhoneNumber();
    }
}

class Ride {
    public function __construct(private Vehicle $vehicle) {}

    // Ride exposes exactly what a notifier needs — nothing about HOW it's structured internally
    public function getDriverPhoneNumber(): string {
        return $this->vehicle->getDriverPhoneNumber();
    }
}

class RideNotifier {
    public function notifyDriver(Ride $ride, string $message): void {
        // ✅ one call, talking only to an immediate friend (Ride)
        $number = $ride->getDriverPhoneNumber();
        $this->sendSms($number, $message);
    }

    private function sendSms(string $number, string $message): void {
        echo "Sending SMS to $number: $message\n";
    }
}
```

Now `RideNotifier` only knows about `Ride`. It has **no idea** that a `Vehicle` or `Driver` or `Phone` even exists. If the internal structure changes tomorrow — say, `Vehicle` starts looking up the driver from a separate `DriverAssignmentService` — `RideNotifier` doesn't need to change at all. Only `Vehicle::getDriverPhoneNumber()` does.

---

## 6. Even better: push the *behavior*, not just the data

Sometimes the best fix isn't "add a getter that reaches through," but to move the actual **behavior** to where the data lives — true "Tell, Don't Ask":

```php
class Driver {
    public function __construct(private Phone $phone) {}

    // Driver knows how to notify itself — callers don't need the number at all
    public function notify(string $message): void {
        echo "Sending SMS to {$this->phone->getNumber()}: $message\n";
    }
}

class Vehicle {
    public function __construct(private Driver $driver) {}

    public function notifyDriver(string $message): void {
        $this->driver->notify($message);
    }
}

class Ride {
    public function __construct(private Vehicle $vehicle) {}

    public function notifyDriver(string $message): void {
        $this->vehicle->notifyDriver($message);
    }
}

class RideNotifier {
    public function notifyDriver(Ride $ride, string $message): void {
        // ✅ Ride is TOLD to notify its driver — RideNotifier never sees a phone number at all
        $ride->notifyDriver($message);
    }
}
```

This version is even more LoD-compliant: `RideNotifier` never even sees a phone number — it just tells the `Ride` what to do, and each object handles its own piece.

---

## 7. Benefits of the Law of Demeter

- **Loose coupling** — classes depend only on their direct collaborators, not on distant internal structure
- **Easier refactoring** — internal structure of `Driver`/`Vehicle`/`Phone` can change freely without breaking unrelated code like `RideNotifier`
- **Easier testing** — you can test `RideNotifier` with a simple mock/stub of `Ride`, instead of constructing a full object graph
- **Clearer responsibility** — each class exposes *behavior* relevant to its callers, rather than exposing its guts

## 8. Common Questions About LoD

**Q: Does this mean I can never call a getter on a returned object?**
No. LoD is about not **chaining across multiple objects you don't own**. Calling one getter on an object passed to you (`$ride->getStatus()`) is fine — it's calling a getter *on the result of a getter, on the result of a getter...* that violates it.

**Q: What about fluent/builder APIs, like `$query->where(...)->orderBy(...)->limit(10)`?**
This is a common (and generally accepted) exception. In a fluent builder, each method **returns `$this`** (the same object), not a different collaborator object — so you're still only ever talking to one "friend." That's different from `$a->getB()->getC()`, where each call returns a *different* object.

```php
class QueryBuilder {
    public function where(string $cond): static { /* ... */ return $this; }
    public function orderBy(string $col): static { /* ... */ return $this; }
    public function limit(int $n): static { /* ... */ return $this; }
}

// ✅ fine — every call returns $this, not a new stranger object
$results = (new QueryBuilder())->where('active = 1')->orderBy('name')->limit(10);
```

**Q: Isn't adding a `getDriverPhoneNumber()` "pass-through" method to `Ride` and `Vehicle` also kind of ugly?**
It can feel like boilerplate, yes — that's a real, honest tradeoff of LoD. You're trading a few extra small delegating methods for much lower coupling. In practice, you don't blindly apply this to every chain — apply it where the chain crosses a real architectural boundary (e.g., across layers, across modules, across classes owned by different teams). For simple, tightly-related value objects within the same small feature, a short chain is sometimes pragmatic (see below).

**Q: Is LoD an absolute rule?**
No — like KISS/DRY/YAGNI, it's a guideline that trades off against others. Overusing "wrapper" methods everywhere to avoid *any* chaining can itself become boilerplate-heavy and violate KISS. Use judgment (see next section).

## 9. When it's OK to bend LoD

- **Simple data/value objects with stable structure** — e.g., accessing `$address->getCity()->getName()` where `City` is a small, stable value object that's very unlikely to change shape, is usually harmless in practice.
- **DTOs used purely for data transfer** (not behavior) — LoD is really about protecting **behavioral encapsulation**, not about banning all nested data access. Reading `$response->getData()->items` in a simple API response DTO is a different situation from reaching through live domain objects with business logic.
- **Fluent/builder patterns**, as shown above — chaining calls that all return `$this` is fine.
- **Framework/library conventions** — e.g., Laravel's `$request->user()->profile->avatar` pattern is common and accepted in that ecosystem, because these are largely read-only, stable data accessors, not business-logic objects whose internal structure is expected to change.

**Rule of thumb:** LoD matters most for objects with **behavior and business logic that changes over time** (domain objects, services). It matters much less for **simple, stable data structures**.

## 10. Practical Example: Ride Notification (Full Before/After)

**❌ Before — train wreck, tightly coupled:**
```php
$number = $ride->getVehicle()->getDriver()->getPhone()->getNumber();
$this->sendSms($number, $message);
```

**✅ After — LoD-compliant, "Tell, Don't Ask":**
```php
$ride->notifyDriver($message);
```

The second version is shorter, doesn't leak `Ride`'s internal object graph to the caller, and survives internal refactors of `Vehicle`, `Driver`, or `Phone` without any change to `RideNotifier`.

---

## 11. Quick Reference

**Law of Demeter**
- Only call methods on: yourself, your parameters, objects you create, your own direct fields
- Avoid chains like `$a->getB()->getC()->getD()`
- Fix: add a small delegating method on the immediate friend (`Ride::notifyDriver()`), or better, move behavior to where the data lives ("Tell, Don't Ask")
- Exceptions: fluent builders (`$this`-returning chains), stable simple value objects, plain DTOs

**In one sentence:** Talk to your friends, not to your friends' friends — and better yet, tell your friend what to do instead of asking them for their friend's stuff.

---

## 12. How LoD fits with KISS, DRY, YAGNI

| Principle | Protects against |
|---|---|
| YAGNI | Building things you don't need yet |
| KISS | Building things in a more complicated way than necessary |
| DRY | Repeating the same knowledge/logic in multiple places |
| **LoD** | **Objects knowing too much about each other's internal structure** |

They complement each other: DRY might tempt you to extract a shared "reach-through" helper (`getDriverPhoneNumber($ride)`) — LoD pushes you instead to put that responsibility inside the object that owns the data, keeping both principles satisfied.
